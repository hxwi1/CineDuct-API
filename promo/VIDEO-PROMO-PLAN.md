# CineDuct 宣传片 方案

做一条两分钟以内的片子，全用 HTML 动画渲染，投 B 站。片子只有一个主角：这个模组在 Minecraft 里做到了显存零拷贝播放。其他能力一句带过。

先说一件会影响片子调子的事。零拷贝这件事不能拿"稳"当卖点：现在是 alpha，链路靠的是显卡驱动提供的那套互操作，换台机器、换个驱动就是另一个结果。这话得在片子里讲明白，不然到时候弹幕第一条就是"我的机器打不开"。

数据你给了，我按截图里的读数重写了那一段，数字列在后面，你核一遍。原来那条 2681 帧零失败的说法我没挂在嘴边了，太像在保证什么。

## 零拷贝（这个镜头要写细）

三拍，二十来秒。

**第一拍，解码就落在显存。** 左边 FFmpeg 和 D3D11VA 的标签亮起来，解码器吐出来的东西直接落在显存框里的一小块纹理上。右边系统内存那个框全程空着、灰的，一条虚线箭头打到框上被弹回去。字幕：硬解输出直接就是一张 D3D11 纹理，帧没进过系统内存。

**第二拍，跨进程。** 四个槽轮流转，每个槽上挂 NT handle 和 KeyedMutex 两个小标签。然后是锁、采样、解锁三个动作，我原想用两只手开合来表示，不行就改成红绿闪一下。上方那条老路径的红线在这里被剪断，剪断的时候静音半秒，低频进来。全片就这一下，别处不许用。

**第三拍，顺手干完的活。** NV12 进 VideoProcessor，出来是 BGRA8，同时把 4K 缩成 1080p 写进槽里。方块体积从 33MB 缩到 8MB。这一拍收住，屏幕重新亮。

措辞上只说没有 CPU 拷贝、不经过系统内存。设计文档里有 GPU 到 GPU 拷本地纹理这一档，说成显存里一次拷贝都没有会被抓。

这里还要说一句：第二拍到第三拍之间怎么过渡我还没想好，可能直接硬切。

## 其他镜头

**印章。** 印章砸下来，震一下，冲击波散开，小字依次淡入。这枚印章片尾再出现一次，压成 30% 当背景。

**老做法。** 光点沿着老管线跑：硬解出来的帧先下载到系统内存，再上传回显存，来回两趟。经过这两段时留下红色计数，右下角读数往上爬：搬运次数、白搬带宽、CPU 占用条。音效是密集 click 叠成的噪音，镜头结束时骤停。这段让人自己算出荒谬感，不用多说。

这里别写成"老办法用软解"。进程内引擎同样是硬解，差别只在帧要下来一趟再上去一趟，这个反差正好是后面那组数据的伏笔。

**实测。** 放你给的这张截图，把 F3 和任务管理器裁出来放大：8192×4320 在跑，零拷贝，游戏帧率 514。

真正能说明问题的是另一组：同一个场景、一样是硬解，把零拷贝关掉走进程内，4K 只有 60 上下。分辨率更低，帧率反而掉下来了，中间差的就是那两趟搬运。所以零拷贝在这不是"快一点"，是搬不搬得起的问题。

再补一句极限：8K 要是走进程内，无法正常播放，游戏进程会卡死。

1080p 或 4K 的开 / 关对照你要是愿意测，那组数可以补进来做成两根柱子，但别为难自己，8K 的不测。

**边界。** 紧跟着上面，不换场，把话说清楚：这是 RTX 5060 Ti、驱动 616.64、Windows 上的一次读数。零拷贝靠显卡驱动给 GL 和 D3D 做互操作，AMD 卡没有这套东西，N 卡也得看驱动版本，所以同一份 jar 在不同机器上不一样。现在还是 alpha，开得起来就播，开不起来就走回退，回退之后还是能看，只是走 CPU 上传。

画面右下角挂一行小字，从头挂到尾：部分情况视设备而定，内存频率、超频、驱动版本都会让结果不一样。这行必须有，发出去一定有人自己测，测出来跟你不一样，这行就是垫子。

这一段里不出现"稳"、"零掉帧"、"完美"。要说的是这条链路在一台机器上确实跑通了，不是它到处都能跑。每帧左上角编帧号、校验端回读比对那个细节我挺喜欢，但塞不下了，看能不能当个两秒彩蛋闪过，塞不进就砍。

**对比。** 五行，逐行扫出勾和叉。WaterMedia 那一列写保守些，下面配一行致敬。表格我拿不准要不要放，见最后。

**快闪。** 六张卡各两三秒，鼓点卡位。关键词直接印在卡上，不再另外出字幕。这段只求扫过去，不求讲清。

**安装。** 三行勾，右边 MC 1.21.1 / NeoForge 21.1.231+ / Java 21 / Windows，底下一行小字：零拷贝要 NVIDIA 那套互操作，我测试用的是 21.1.251 + RTX 5060 Ti，别的环境会回退。

**片尾。** 印章当背景，logo 落位，仓库地址写成文字，最后淡出。

## 准备上屏的数字

能当场算的：

- 1080p60 单帧 1920×1080×4 ≈ 8.3MB。单程 0.5GB/s；进程内是下去再上来，一来一回 1GB/s。4K60 单程 2GB/s，来回 4GB/s。
- 槽位 33MB → 8MB（4K 解、1080p 输出）。

从你那张截图读出来的（截图 2559×1439，我按上面能看清的行抄的）：

- Minecraft 1.21.1，NeoForge 21.1.251
- 片源 8192×4320
- 游戏帧率 524，p50 514，p98 345，p99.5 297
- CPU 37%（3.79GHz），GPU 37%，显存 6.3 / 16.0 GB，49°C
- RTX 5060 Ti，驱动 616.64

你自己补的一笔：同一个场景、一样是硬解，关掉零拷贝走进程内播 4K 24fps，游戏帧率在 60 上下浮动。

严格说这不算同一组实验，分辨率不一样（8K 对 4K），但方向对得上：差别不在解码，在搬运。如果 60 上下其实是垂直同步或者 60Hz 封顶，实际只会更低，对论点更有利，不过片子里别猜，就写"60 上下浮动"。

帧率数字的用法就一个：8K 不搬能跑起来，4K 一搬就往下掉。别引申成"性能提升百分之几"。

顺带一个更好的细节：那部 4K 片是 24 帧的，每帧 33MB 上下，一秒搬下来再搬上去也就 1.6GB/s 左右，比 4K60 少一半还多，结果照样把帧率压到 60 上下。这个反差比"8K 对 4K"更说明问题——搬运这活儿贵得离谱。

画面上建议标"这台机器"。别写"几乎不影响帧率"。

对照这件事缩小范围：8K 不做进程内测试，那个组合不是慢，是无法正常播放、进程会卡死。真要对照就挑 1080p 或 4K，一边 `/cineduct subprocess on`，一边 `/cineduct fallback` 压回进程内，同一个场景各录一遍。1080p 下进程内引擎是能跑的，风险为零。做出来就是两根柱子，比截图直观；不做也不影响片子成立。

原来那条 4K60 跑 45 秒、2681 帧、拷贝失败 0、锁失败 0、音画偏差 <40ms（出自 docs/PLAN-standalone-gpu.md 打样记录）偏"保证"，按你的意思先不用，想用再说。

要你给的（可选，不做也行）：1080p 下的开 / 关对照。8K 别碰。

## 我没想好的几处

1. 你给的截图里有影视飓风那支 8K 演示片的画面，那片 B 站标了禁止转载。片子里还要不要出现这段画面？我倾向只留 F3 和任务管理器的读数，画面本身虚化或裁掉，字幕里写一句片源是影视飓风的 8K 演示片，简介鸣谢。这个得你定。
2. 三级降级链（dxgi-interop → shm → java）对外讲不讲。README 只写两级，讲多了跟文档对不上，但三级其实更能说明"总有路可退"。这个想听你的。
3. 对比表会不会让 WaterMedia 那边不舒服。我倾向只列事实加一行致敬，但也可能干脆不放这一列，改成口播一句"上一代是 CPU 上传"。
4. 第二拍那三个动作怎么画才不像教学片。我想先做个五秒动态稿给你看，再定。
5. 要不要旁白。全字幕两分钟看着累，但配音一进来就容易变成宣传片腔。
6. 106 秒是我拍的，剪完可能一百一也可能九十几，先不锁死。
7. 4K 那次垂直同步开没开、显示器是不是 60Hz？如果也关着，60 就是真掉，这段完全成立；如果开着，那实际比 60 更差，说法不用改，只是别写具体倍数。
8. S5 里 8K 那句按你说的写成"无法正常播放，游戏进程会卡死"。只提醒一点：如果你没真跑过一次，这句就是推断出来的结果，有人真去试、结果只是掉到十几帧没卡死，就会说这视频夸张。要软化成"跑不了"也行，你定。

## 标题

三个方向，不是一句话换三种说法：

- 技术向：DXGI 共享纹理直通 OpenGL，我在 Minecraft 里做了显存零拷贝播放
- 玩梗向：Minecraft 里看 B 站，帧都没出过显卡
- 搜索向：Minecraft 模组推荐｜在游戏里放块屏幕看视频（CineDuct API）

我觉得第二个传播最好，第一个更对技术区口味，但这是我猜的。
