# 开发约定（CineDuct API / MediaFix）

> 这份是给"以后回来的我"看的。踩过的坑都写在这儿，免得重复。

## 1. 测试只在 dev 客户端做 —— 不要部署到用户的正式实例

```powershell
.\gradlew.bat runClient        # dev 客户端；gamedir = 工程下的 run/
```

**不要**把 jar 拷到 `F:\potato world\.minecraft\versions\Potato World 26.9.17\mods`。
那是用户的正式游玩实例，上面跑的是**备份版（前置 mod 时代）的 jar**，与本工程当前的独立版没有关系。
在那边部署会同时出现两个模组（modid 不同、机制完全不同），而且用户明确要求过：**只走 runClient**。

dev 环境的关键路径：

| 东西 | 位置 |
| --- | --- |
| dev 游戏目录 | `<工程>/run/` |
| dev 配置 | `run/cineduct-ffmpeg.json`、`cineduct-stream.json`、`cineduct-log.json`、`cineduct-bili.json` |
| dev 日志 | `run/cineductlogs/` |
| FFmpeg DLL | `run/cineduct-ffmpeg/v2-bundled-*/`（由 `FfmpegRuntime` 从 bundle zip 解压） |
| 原生产物 | `native/build/bin/cineduct-host.exe`、`cineduct-glshim.dll` |
| 原生产物的 dev 投放点 | `build/resources/main/cineduct-native/`（由 `processResources` 自动拷贝） |

## 2. 命名约定

- **modid / 指令 / 配置文件名 / 原生产物名 = `cineduct*`**
  - 指令：`/cineduct screen ...`、`/cineduct-stream ...`
  - 配置：`cineduct-ffmpeg.json` 等；日志目录 `cineductlogs/`；natives `cineduct-native/`
  - 显示名：**CineDuct API**（`mods.toml` 的 `displayName`）
- **Java 包名保持 `dev.mediafix` 不动**（用户明确要求；JNI 符号名由包名推导，也不能改）
- 改 `MODID` 时记得 `gradle.properties` 的 `mod_id` 必须同步 —— 二者不一致会让游戏**起不来**
  （曾经发生过：常量还是 `"mediafix"`，`mods.toml` 已经是 `cineduct`）

## 3. 构建

```powershell
.\native\build.ps1 -NoJava     # 只编原生（默认全量重建，几十秒）
.\native\build.ps1             # 原生 + Java 侧打样消费者
.\gradlew.bat build            # 模组 jar
```

- **原生默认全量重建**：CMake 4.3 生成的 ninja 规则没有 `deps =`，头文件依赖跟踪不可靠，
  曾因此出现"改了没生效 / 结构体布局不一致 → 调野指针崩溃"。要用增量就显式 `-Incremental`。
- **`.ps1` 文件必须 UTF-8 带 BOM**（PowerShell 5.1 否则把中文读成乱码直接语法报错）。
  用脚本批量改 `.ps1` 后要重新补 BOM。
- 用 PowerShell 批量做字符串替换时，**不要把替换对写成嵌套数组**——会被展平成字符串，
  于是 `Replace($r[0], $r[1])` 退化成**单字符替换**（我干过一次：`g→e`、`C→o`、`.`→`r`，
  一次污染 6 个文件）。用扁平数组步长 2，或者写成 `[pscustomobject]@{Old=..;New=..}`。

## 4.5 直播（live）在子进程模式下的两个专属坑（2026-09-26 实测）

两句结论，改 HTTP 请求或时间轴相关代码前先读：

1. **子进程必须显式给 User-Agent。**
   FFmpeg 自己的 UA 是 `Lavf/8.0.1`，B 站**直播** CDN（`live-bvc`）直接回
   `403 Forbidden (-858797304)`；点播 CDN（`bilivideo`/`mcdn`）不挑 UA，所以这个坑只在直播上暴露。
   Java 侧一直有 UA（`FfmpegVideoSource.UA`），子进程以前没传 → 同一条直链、同一份 Referer/Cookie，
   进程内引擎能打开、子进程 403 退出。现在 `HostSession` 传 `--user-agent`，`main.cpp` 也有同一个默认值。
   复现/验证：`.\native\live-smoke.ps1`（对照组用 `--user-agent Lavf/8.0.1`，必须复现 403）。
   **UA 要一路传到底**：音频是"另开一路输入"去拉同一条流的（`probeAudio` / `AudioSource::open` /
   `AudioBitstream::openInput`），任何一处漏了 UA，直播就变成**有画面没声音**
   （日志：`音频不可用，改为纯视频: 打不开音频链`）。新增打开输入的代码请一律带 `userAgent`。
   注：B 站不同 CDN 节点校验严格程度不一样（有的节点 Lavf UA 也放行），所以"对照没复现 403"不等于没这回事。
2. **直播的 PTS 不从 0 起，必须做"时间轴原点"归一。**
   点播 PTS 从 0 起；直播 PTS 是"开播以来的毫秒数"（实测 `2356949ms` ≈ 39 分钟）。
   而音频时钟在首帧发布时被锚定成 0（`anchorClock(0)`），拿原始 PTS 去比 → 子进程要等 39 分钟
   才允许放第一帧，表现是"握手 ok、就是一直没画面"。
   现在所有时间轴比较统一用 `mediaPtsMs = pts − 首帧 PTS`（点播原点为 0，行为不变）。
3. **（未查清的角落）直播 + `--spdif-dump` 会卡住**：UA 修好后音频探测能过，于是直通自检那条路第一次
   真的跑到"读直播流"上，实测 6 秒的 dump 跑不完（疑似 `close()` 里 join 泵线程时它正阻塞在网络读上，
   直播流永远不会 EOF）。**不影响正常使用**：`audioMode` 默认 `shared`、直播音轨是 AAC（不会进直通），
   这个自检只在显式 `--spdif-dump` 时走。以后要查就从 `AudioBitstream::close/quit` 与 `rw_timeout` 入手。

## 4.6 屏幕闪烁 = "没帧时什么都不画"

Java 传输下 `MediaSession.acquireDrawTexture` 拿不到新帧时会返回 -1 → 渲染器那一帧**什么都不画**，
玩家看到屏幕一闪一闪（直播缓冲薄、反复进出 BUFFERING 时尤其明显）。
现在改为**保持上一帧**（纹理里还有旧内容，直接当本帧纹理画出去），只有"一帧都没上传过"才留空。
子进程传输本来就是这个行为（`drawSlot` 保持上一槽位）。

## 4.6.1 "画面会闪 / 帧顺序像乱了"（2026-09-27 两次改错之后的最终结论）

**先看现象分三类，各有各的指纹**：

| 日志指纹 | 触发者 | 性质 |
| --- | --- | --- |
| `会话 #N 帧号回退 #N：槽 x 拿到帧号 a，上次已是 b` | **消费者挑了比上一帧更旧的槽位残留**（本模组自己的 bug） | **真的往回画旧帧 = 闪**。现场实测 25 秒 200 次 |
| `会话 #N 显示面比例改为 x → 重开子进程以换输出尺寸` | 附属模组在**显示面第一次渲染**时才算比例（compat `DisplayRendererMixin` 是 `vertex` 重定向，比同一次渲染里的取帧更晚） | 每开一块屏白起一次子进程：**慢 ~2.5 秒**（此时还没画过帧，所以是"慢"不是"闪"） |
| `独立播放器 #N 已重建会话 #N` | 附属模组（waterframes **刷新按钮**/`reload_all`） | 黑 ~1.2 秒 + 续播 seek；**按了刷新才有，不是 bug** |

### 第一类（真正的闪）：槽位残留导致往回画

```
槽 1 = READY(帧 10)   槽 2 = READY(帧 9)      ← 生产者的两次发布都还没被取走
消费者挑最高帧号 → 画槽 1（帧 10）✓，把槽 1 标成 SHOWN
生产者还没发下一帧；
消费者下一帧再挑 → 槽 1 不算，只剩槽 2 = READY(帧 9) → **画了帧 9（往回跳）**
```

客户端帧率高于视频帧率（59.94fps）时每帧都可能撞上。修法两条（都已落地）：
1. `HostSession.dropStaleSlots(gen)`：画完最新一帧就把**帧号不大于它**的 READY 槽位全标成已取用
   —— 它们已被时间甩掉，留着只会制造"往回画"的机会；
2. `MediaSession` 单调性守卫：万一只挑到更旧的帧，**保持上一帧**（上一槽位的本地纹理是快照，
   生产者只写共享纹理，不会动它），计数打到 `保持上一帧第 N 次`（正常应恒为 0）。

**教训**：前两轮都改错了方向 —— 一次去动生产者的槽位互斥（把生产者冻死），
一次改去治"子进程重开"。**在 `帧号回退` 探针给出数字之前，不要动同步代码。**

### 第二类：开屏那次"白起一次子进程"

零拷贝输出尺寸只有开进程时能定，所以想要"比例后到"不重开，只能**别那么早起进程**：
`MediaSession.hostSpawnPending` —— 会话创建时先不起，**等到第二帧取帧**（第一帧时比例还没推过来）、
或 1.5 秒兜底（自带 `cineduct-host-defer-N` 守护线程，**不能指望 tick**：
`Sessions.tickHealth()` 实测只在"退出世界那一 tick"被调用）才起。
配套：`setDisplayAspect` 阈值从固定 0.005 放宽到 **1%**（附属模组每帧都算一次比例，
16:9 的 1.7778 与脸面的 1.7727 只差 0.0051，卡在旧阈值上会**来回重开**）。


## 4.6.2 "两条音频一起播放" = HOST 模式掉进了 Java 兜底（2026-09-27 自己踩的）

**症状**：一个视频同时有两路声音，其中一路**不受指令控制**（音量/暂停都管不到它），但内容确实是同一个视频的。

**日志指纹**（一眼就能认）：

```
会话 #1 已创建: transport=(子进程启动中)
会话 #1 进程内引擎已启动        ← 0.3 秒后，第二条链：自己开了一块声卡
子进程已启动: pid=50272         ← 0.6 秒后，第一条链
```

**成因**：`acquireDrawTexture()` 里 HOST 分支的旧写法是 `if (mode == HOST && host != null) {…}`，
然后**落到下面的 Java 兜底**；而那句兜底会 `ensureEngine()`。只要出现"mode 已定为 HOST、但 host 还没建好"
的窗口（推迟启动、重建中的空档），取帧就会**真的把进程内引擎建起来** —— 于是两块声卡同时出声。
指令只发给子进程，所以玩家听到的是"另一条不受控制"。

**三条不变式（已落地，别再破）**：
1. `acquireDrawTexture`：`mode == HOST` 时**绝不落到 Java 兜底**，没子进程就返回 `-1`；
2. `ensureEngine()`：**只允许 `mode == JAVA`** 时建（要降级请走 `failHost()`，它会先把 mode 切成 JAVA）；
3. `spawnHostNow()`：起子进程前，把这条会话上**已存在的**引擎先关掉（防御历史状态）。

## 4.7 LWJGL 的"没有上下文"是抛异常，不是返回 null

`GL.getCapabilities()` 在没有当前 GL 上下文时**抛 `IllegalStateException`**
（`No GLCapabilities instance set for the current thread…`），不会返回 null。
实测过（脱离游戏、只有 lwjgl + lwjgl-opengl + natives 在 classpath 时跑一句就复现）。

所以**任何"探不到就退化"的兜底都不能靠判 null**：
- `GpuContext.probe()` 曾经写成 `if (GL.getCapabilities() == null)` → 那行是死代码，
  后台线程误调会把异常抛穿，而不是像注释写的那样"退回进程内引擎"。现在整段包了 try/catch。
- 新增"要调 GL 函数才能拿到的东西"（适配器 LUID、GL 版本、扩展）时，一律：
  **在调用方所在线程先探一次**（通常是渲染线程，见 `ScreenClientState.update()` /
  `CinePlayerApiImpl.open()`），并且**探测函数自己吞掉 IllegalStateException**。
- 反面教材：把探测放在 `RenderSystem.isOnRenderThread()` 条件里、又放在后台线程上 ——
  等于永远探不到（独立播放器 API 第一版就是这么写的，被调用方踩到了）。

## 6. 音画不同步的排查指纹（2026-09-27 踩过）
症状：放着放着音画错开，而且**一次之后再也不回来**。

日志指纹（子进程侧）：

```
seek -> 2ms（视频=ok 音频=ok）        ← 有 seek
（再也没有“音频已定位到 2ms”）        ← 音频解码线程没在执行请求
音频时钟停滞超过 3 秒，已改挂钟节奏    ← 3 秒后时钟被判死
（之后所有 seek 都显示 音频=无音频）
```

根因：`AudioSource::decodeLoop()` 读不到包（片尾）时排空解码器就 `return` 收摊，
而 `seek()` 只登记请求、等解码线程去执行 —— 线程没了请求就永久没人执行，音频时钟停住，
3 秒后被判成"音频链已死"，画面永久改挂钟节奏。**片尾是常态**（放完 / 跳到结尾 / 循环前一刻），
所以这条路上任何一次 seek 都会踩中。

结论与约定：
- **带"请求队列"的后台线程永远不要在片尾退出** —— 排空之后要留一条"等命令"的活路
  （`while (!quit && requestSeekMs < 0) sleep(10ms);`），否则"之后还能不能 seek"就永久坏了；
- **音频时钟必须用 `playedFrames()`**（写入 − flush 丢弃 − 设备缓冲未播），不能用
  `framesWritten() - pendingFrames()`：后者把 `flush()`（设备 Stop）丢掉的那段也算成"播过了"，
  时钟会凭空前跳，画面跟着提前；
- **"时钟停滞 → 永久改挂钟"这种一次性降级要配一条恢复路径**：恢复后要重新对表
  （画面领先就请求音频 seek 追上），否则一次卡顿 = 永久错位。

验证手段：`native/eof-test.ps1`（片尾存活 / 片尾后 seek / 回卷 / 暂停冻结 / 暂停中 seek / 恢复）。

## 6.5 音画偏移：**先分清"逻辑错位"还是"物理延迟"**

两种情况长得像，处理方式完全相反：

| | 逻辑错位（bug） | 物理延迟（正常现象） |
| --- | --- | --- |
| 特征 | 越放越偏、seek 后跳一下、无声音后画面继续跑 | **固定量**，一直稳定地差那么多；画面领先声音 |
| 日志 | `音频时钟停滞…` / `音频已定位到 …` 缺失 / 时钟速率异常 | 什么都正常，`已发布` 帧率稳定 |
| 处理 | 查时钟链路（见上一节） | 用偏移量补偿（`/cineduct av <ms>`） |

物理延迟的来源：画面是在"音频设备把这一段播出去"的时刻放出去的，而声音从设备缓冲到**耳朵**
还要过 HDMI → 功放/回音壁的处理。设备自报的延迟基本是 0（实测 `设备报的流延迟: 0ms（引擎周期 10.0ms）`），
所以只能靠人耳/眼睛调。

**标定方法**（本机那次定为 -260ms）：
1. 放一个**有说话或打点**的视频；
2. `/cineduct av -60` 起，按 -60 一档往下加（-120 / -180 / -240…），到对得上为止；调过头就往回加；
3. 定下来会写进游戏目录根的 `cineduct-ffmpeg.json`（`avOffsetMs`），下次启动继续用；
4. **换输出设备要重调**（换到耳机/音箱 / 换回音壁 → 值完全不同，通常耳机就是 0）。

> 这条值只能"看着调"，所以做成了运行期可改（零拷贝走控制通道 `av-offset` 动词、进程内引擎下一帧生效），
> 不要把它做回启动参数 —— 那样每试一档都要重启一次游戏。

## 6.6 共享纹理槽位协议（2026-09-27 试过收紧，**已回退**）

子进程发帧 → 消费者取帧这条路上有两条**设计意图**，但其中第二把兜底**实测不能删**：

1. **写方优先选 EMPTY / SHOWN 的槽位，没有空闲槽位就丢帧。**
2. **键控互斥：写方拿 writer key（0）、读方拿 reader key（1）。**

> ★ **这一节原来的结论是错的，留在这里当反面教材。**
> 曾经按"两条铁律"把"没空闲槽位时 `nextSlot++ % N` 的盲选"和"超时就试另一把钥匙"全都删掉，
> 结果**生产者直接冻死**（`发布` 帧数不再增长、画面卡住），用户当场报"改完更严重"。
> 现在的代码是**回退后的状态**：盲选兜底与"超时试另一把钥匙"都保留
> （见 `native/host/src/shared_tex.cpp` 与 `native/glshim/src/cineduct_glshim.cpp` 里的★注释）。
>
> 而且"画面会闪"最终证明**不是**槽位协议造成的，而是**子进程被反复重开**（见 §4.6.1）。
> **教训**：改同步/槽位代码之前，先让 `帧号回退` 探针（§4.6.1）给出证据 —— 不能凭"看起来像撕裂"就动协议。

由此带来一个**必须记住的副作用**：没有人取帧时（屏幕被视锥剔除、玩家看向别处），
写方拿不到交还的槽位与钥匙，就会停止发新帧（只丢帧）。这是正常的、省资源的 ——
所以健康检查**必须**先看"最近有没有人来取帧"（`MediaSession.lastDrawRequestAt`），
否则会把这种正常情况判成"子进程卡死"并反复重启。

验证手段（不需要游戏）：不给消费者跑子进程，
`输出纹理` 那里应该看到"发布 3 帧（=槽位数）之后开始丢帧"，而**不是**发布帧数一直涨。

## 8. 子进程流水线（v2，2026-09-28 按 CicadaPlayer 的分层重写）

**背景**：`cineduct-host` 原来是一条 1700 行的"什么都干"的主循环 —— 读包 → 送解码器 → 收帧 →
转换 → 发布 → 等时钟全在一个线程里，而且"等音频时钟"是 2ms 轮询。后果：网络抖一下画面就停摆、
seek 只能排队、落后了没有丢帧策略、硬解打不开就整个进程退出。现在按成熟播放器的结构拆开了。

```
[demux 线程]  av_read_frame ──► 包队列（60 包 / 8MB，满了睡；打断回调挂在 AVFormatContext 上）
     ▲                              │  所有阻塞等待都能被 seek / 停止唤醒
     │ interrupt_callback           ▼
[解码线程]  avcodec_send/receive ──► 帧队列（3 帧，满了等而不是丢）
     ▲                              │
     │                              ▼
[呈现线程 = main 线程]  主时钟判定（等 / 丢）──► 转换 ──► 共享纹理 ──► 状态块
```

**seek = 三阶段握手**（每段由各自的线程做，靠一个递增的"世代号" `seek.generation` 对齐；
跨世代的包/帧在**出队时**丢掉 —— 这是"seek 之后先吐出来的旧包不会被解成画面"的保证）：

| 阶段 | 线程 | 做什么 |
| --- | --- | --- |
| 1 | demux | `avformat_seek_file`（带 ±2s 窗口）→ 退化到 `av_seek_frame(BACKWARD)`；清包队列 |
| 2 | 解码 | `avcodec_flush_buffers` + 清帧队列的片尾标记 |
| 3 | 呈现 | 作废时钟、清声卡缓冲、请求音频定位、置前导帧丢弃阈值（preroll） |

**出帧判定**（数值取向对照 CicadaPlayer 的 `RenderVideo`）：

- 早于主时钟 10ms 以内 → 等；每次最多等 20ms（好让停滞/暂停/seek 及时被看到），
  累计等满 2 秒就**强行出帧**（宁可早，不可饿死画面）；
- 晚于 100ms **且帧队列里还有更新的帧** → 丢这一帧（队列空着不丢 —— 宁晚不空）。

**时钟**（`media_clock.*`）：有音频就以"声卡已播出的采样数"为主时钟（`playedFrames()`，
已扣掉 flush 丢弃的那段）；停滞超过 3 秒退到挂钟；**恢复路径**：音频又走了（>250ms）就回到
音频基准，画面领先 >300ms 就把音频 seek 上去追 —— **一次性降级必须配恢复路径**（§6 的教训）。

### 8.1 这一轮修掉的真 bug（都是"看起来正常、实际在丢东西"的类型）

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| 硬解缓冲吃紧时成片丢帧 | `avcodec_send_packet` 返回 `EAGAIN` 被当成错误 `continue`，那个包被 unref 掉 | `EAGAIN` = "先把帧收掉再重发这个包"，包必须保留 |
| 硬解打不开的流整个子进程退出（只能回退进程内引擎） | `avcodec_open2` 失败直接 `return 6` | 硬解失败 → 软解重开；运行期连续报错 ≥5 帧 → 换软解；设备没有可用 `ID3D11VideoProcessor` 时硬解帧回拷 CPU 再转 |
| 纯挂钟模式（`--no-audio`）4 秒只出 1 帧 | `anchorWall()` 忘了置 `isAnchored` → 时钟永远停在 0，每帧都判定"太早" | 置 `isAnchored`；并且**等待不再丢帧**（丢帧只由"迟到"判据决定） |
| 起播瞬间就打"音频时钟停滞 3 秒"，之后画面永久走挂钟 | 时钟的"上次推进时刻"用默认构造值（= 时钟纪元，等于几十年没推进） | 构造时初始化为 `now()` |
| seek 之后画面再也不出来（位置停在旧值然后判片尾） | 帧的世代**就地取** `decodeDone`，而 demux 可能已经推进了新包 → 新帧被标成旧世代、被呈现侧过滤掉 | 帧的世代**继承包的世代**（包在入队时就有正确世代） |
| 暂停之后还会推一帧（上层看到"暂停了画面还在动"） | 渲染线程可能在暂停命令到达的同一瞬间已取到帧，或正卡在等时钟的循环里 | 出画面前再查一次 `paused`（除"seek 后的第一帧"）；等时钟的循环也要能被暂停打断 |
| 暂停期间位置还在慢慢爬 | 声卡 `Stop()` 要几毫秒才真停，设备待播数会抖 | 暂停位置在按下那一刻钉死（`pausedPositionMs`） |
| 退出时可能挂死 | 音频解码线程卡在声卡背压（`write` 等待）里，而链路 `close()` 要 join 它 | 收尾顺序：`abortWrites()` → 链路 `close()` → 声卡 `close()` |
| **跳转之后变成"播放结束"** | 某些流的定位"看起来成功、实际读不下去"（实测 TS：`ffmpeg -ss 4` 都解不出帧），旧代码把这次的 EOF 当片尾上报 | **定位自愈阶梯**：换单点定位 → 退回目标前 2 秒 → 回起点 → 放弃（最多 3 次）。判据放在**呈现侧**："这个 seek 纪元连一帧都没放出来就 EOF" |
| 起播时音画内容差 0.3~1 秒 | 音频链提前起播，等第一帧画面出来时声音已经播了一段 | 首帧处做一次"对表"：点播把音频 seek 回同一起点（直播不动 —— 直播没有起点可回） |

### 8.2 定位自愈的判据为什么放在呈现侧（**别再挪回 demux 侧**）

试过在 demux 侧判"刚 seek 完就 EOF，而且读到的位置离片尾还远"，结果**连点进度条时每一次
"读被新的 seek 打断"都像是一次坏定位** —— 多余的重定位把落点改成了"目标 − 2 秒"，
用户点了 6000 却停在 4000（`pipeline-test.ps1` 的 seek 风暴就是抓这个的）。
呈现侧判据"这个 seek 纪元连一帧都没放出来"只有呈现侧知道，且不会被正常打断污染。

### 8.4 HDR 内容曾经"发灰"——根因与修法（2026-09-28）

**症状**：HDR 内容（B 站 HDR 画质 / HDR10 视频）画面对比度极低、发灰发闷；换成 SDR 源就正常。

**根因**：`convert.cpp` 里把 VideoProcessor 的色彩空间**写死成"BT.709 有限范围 SDR"**。
遇到 PQ/BT.2020（HDR10）内容时，驱动把 PQ 编码值当 SDR 直接映射 —— 高光全被压在一起。
本机实测（`native/testdata/bbb-hdr10.mp4`，与 `bbb.mp4` 同内容、真 HDR10）：

| 情况 | 平均亮度 | 最暗 | **最亮** |
| --- | --- | --- | --- |
| SDR 原片（参考） | 110.2 | 30 | 253 |
| 修之前（= 朴素转换） | 80.9 | 34 | **131** ← 高光被压死，这就是"发灰" |
| 修之后（驱动色调映射） | 55.3 | 0 | **255** ← 动态范围回来 |

**修法**（`convert.cpp::applyColorInfo`）：

1. 从帧上读真实色彩信息（`video_color.*`）：`color_trc`（PQ/HLG）、`colorspace`/`color_primaries`（BT.2020）、
   `color_range`、位深，以及 HDR10 元数据（mastering display / MaxCLL，帧 side data）；
2. 用 `ID3D11VideoContext1::VideoProcessorSetStreamColorSpace1` 把输入声明成
   **`DXGI_COLOR_SPACE_YCBCR_STUDIO_G2084_TOPLEFT_P2020`**（HLG 则是 `..._GHLG_..._P2020`）、
   输出声明成 **`DXGI_COLOR_SPACE_RGB_FULL_G22_NONE_P709`** —— 驱动于是自己做 HDR→SDR 色调映射
   （Windows 视频管线同款做法）；
3. 用 `ID3D11VideoProcessorEnumerator1::CheckVideoProcessorFormatConversion` **先问驱动支不支持**，
   不支持就明确告警（别让人以为"发灰是正常的"）；
4. 有 HDR10 元数据就通过 `VideoProcessorSetStreamHDRMetaData` 交给驱动（它的色调曲线会更贴合内容）；
5. 拿不到 `ID3D11VideoContext1`（老系统/驱动）时退回旧接口并告警 —— 旧接口表达不了 BT.2020/PQ。

**为什么输出是 SDR**：我们的输出是 BGRA8 纹理，最后被 Minecraft 当普通贴图画进 LDR 帧缓冲。
"输出 HDR"没有意义（会被游戏再当 SDR 解释一遍，还是灰），只能做色调映射。

**两个开关**（都是诊断/兜底，Java 不传就用默认值）：

| 开关 | 作用 |
| --- | --- |
| `--hdr-tonemap driver` | **默认**：交给驱动（零额外开销） |
| `--hdr-tonemap cpu` | 硬解帧回拷 CPU，用 `sw_scale.cpp` 里自己写的色调映射（PQ 反 EOTF → BT.2020→709 色域矩阵 → Reinhard 肩部曲线 → BT.709 gamma）。曲线可控，但每帧多一次 GPU→CPU 拷贝 |
| `--hdr-tonemap off` | 关掉（复现"发灰"，`hdr-test.ps1` 用它当对照组） |

**CPU 那条路注意两件事**（都踩过）：
1. `sws_setColorspaceDetails` 的 `table`（目标系数表）**不能传 nullptr** —— swscale 内部会拿它索引，
   实测直接 0xC0000005（minidump 落在 `native/build/bin/`）。两张表都要给全。
2. 色彩标签要**从硬解帧读**：`av_hwframe_transfer_data` 出来的 CPU 帧不保证带 `color_trc`
   （实测丢了），于是 HDR 被当 SDR、色调映射形同不存在。
3. CPU 路径的峰值默认取 1000 nit（HDR10 惯例），**有元数据就用内容的自报峰值** ——
   峰值取错会直接体现为"画面偏暗"。

**验证手段**：`native/hdr-test.ps1`（11 项断言，只靠子进程自己打印的"首帧亮度统计"，不依赖外部工具）：
认出 HDR / 声明给驱动 / 映射后最亮 ≥200 / 关掉后最亮 ≤170（对照组）/ CPU 模式不崩 / SDR 素材不被误判。

#### 8.4.1 硬编码策略：**不拉 HDR 视频流**（2026-09-28，作者决定不处理 HDR）

色调映射那条链路虽然是通的（上面 11 项断言全绿），但只要它有一环错位，现象就是"画面发灰、
高光压死"，而这类问题**只能靠专业播放器逐帧比对**才能判断 —— 投入产出比极低。所以现在的策略是
**从源头避开**：

- `DashResolver.isHdrVideo()` / `withoutHdr()`：选流前先剔掉 HDR（B 站 `qn=125`）与杜比视界
  （`qn=126` / `codecs` 以 `dvh` 开头），再兜一层 codec 名（含 `hdr`、以 `hlg` 开头）。
  这是**唯一入口**：手动档位与 ABR 两条路都吃这份过滤后的列表，ABR 阶梯里也不会再出现 HDR 档。
- 剔完之后如果**一条都不剩**（视频只提供 HDR）：退回选 HDR 并打 warn —— "什么都不放"比
  "放一条 HDR"更糟；此时画面由子进程已有的色调映射兜着（那条链路保留，兼作本地 HDR 文件的保障）。
- `fnval` 仍按原样请求（`4048`，含 HDR/Dolby 档位位），**故意不抠位**：接口会把完整列表给我们，
  过滤发生在本地、结果可预期、日志里能打出"排除了几条"；抠位反而可能让接口少给别的档位（未经验证）。
- 用户侧表现：HDR 视频**自动落到它的最高 SDR 档**（一般 4K 或 1080P60），日志出现
  `已排除 N 条 HDR/杜比视界流（本模组硬编码不拉 HDR），候选 X → Y 档`。
- `/cineduct-stream quality` 本来就没有 HDR 档位，不需要改。
- 判定规则的独立验证：`%TEMP%\cineduct-hdrprobe\HdrFilterProbe.java`（一次性探针，按真实
  B 站 `dash.video` 条目形状跑 14 条断言：HDR/DV/HLG 全部命中，8K AV1、4K HEVC、4K H.264、
  1080P60/+/1080P/720P/480P/360P **一条都没误伤**）。


### 8.5 "暂停之后音画不同步、且不随时间变化"——两个真 bug（2026-09-28）

症状：暂停/跳转之后音画错开一段，**而且再也不纠正**（不漂移，说明是一次性错位，不是时钟速率问题）。
查下来是两个独立的真 bug，合起来正好能造出这个现象。

#### bug 1：`flush()` 把"设备待播"记进了丢弃账，却没真丢

`AudioSink::flush()` 原来是：`Stop()` → `discarded += 待播` → 清环形缓冲。

**实测 `Stop()` 并不会清空设备缓冲**（暂停前后 `GetCurrentPadding` 都是 9600 帧，一点没变）。
于是这一步只让**音频时钟凭空前跳最多 200ms**，那段音频数据却还在缓冲里、之后照旧播出来 ——
画面跟着前跳后的时钟走、声音压着一段旧内容 → **声音永久落在画面后面**。
诊断证据：`playedFrames` 一度算出**负数**（-4320），因为同一批待播帧被算了两遍。

修法：`Stop()` 之后再补一次 **`IAudioClient::Reset()`**（它才是真正丢弃缓冲的调用），
并保持"记了账就等于真丢了"的一致性。

#### bug 2：首帧"对表"用的异步 seek 根本没生效

起播时音频链比画面早跑（打开输入→解码→建共享纹理要 1 秒上下），所以要做"首帧对表"。
原来是用**非阻塞 seek(0)**：只登记请求，等链路线程下一轮开头执行；而链路在我们 flush 之后
会把**它当前解码位置**的内容重新写满整个环形缓冲（1 秒）—— 于是"回到起点"在效果上被冲掉。

实测证据（`--debug-audio-lag 1` 打开 AV 明细）：

| | 起播时"可听内容 vs 画面" |
| --- | --- |
| 异步 seek 对表 | **1194ms**（声音领先一秒多，画面永久落后） |
| 改成**重启链路**对表 | **24ms** |

修法：点播的首帧对表改成 `AudioChain::restart()`（**确定性**地从头开始解码），
代价是一次重开输入（本地可忽略、DASH 多一次快速请求，且只在起播发生一次）。
直播不做对表（直播没有"起点"可回），只清一次缓冲。

#### 顺带修掉的死锁（改 bug 2 时踩到的）

`restart()` 内部要 `close()` → `join` 链路线程，而那条线程正卡在 `sink->write()` 的背压等待里
（环形缓冲满，且**设备被我们特意按住**）→ join 永远等不到 → **整个子进程卡死**（实测跑了 10 分钟没退出）。
修法：加 `AudioSink::interruptWrites()`（只打断**当前这次**等待，不把声卡标记成永久停写），
重启/收尾前先调它，再 `close()`。

#### 新增的诊断与纠正通道

- 状态块 **v5** 追加 `videoPtsMs@392`（最近发布帧的媒体时间）—— 与 `mediaPositionMs`（音频时钟）
  一减就是音画偏移。以前没有它，"音画不同步"只能靠人眼判断。
- 子进程会**每 5 秒最多打一行**偏移日志（只在 |偏移|>300ms 时）：
  `音画偏移 -451ms（声音领先画面；排队 1200ms，可听内容 2490ms，画面 2040ms，已写帧 …，已播帧 …）`
- **可听内容位置** = 音频链"最新写出样本的内容时间" − `AudioSink::queuedDurationMs()`
  （环形缓冲 + 设备待播）。★ 注意**不能**用 `写入 − 已播` 代替排队时长：那个差值是
  `丢弃累计 + 设备待播`，`discarded` 跨 seek 一直累加，实测能差一秒多。
- **自动纠正默认开启，但动的是时钟而不是声卡**（见 8.5.1）。`--av-correct` 保留为
  "把音频 seek 到画面"的老路线（会有听得出来的跳音），默认路线不碰声卡。
- `native/av-sync-test.ps1`：5 条断言（重启链路对表 / 起播对齐 ≤150ms / 注入的偏移被发现 /
  `--av-correct` 纠正通道生效）。
  注入用 `--debug-audio-lag <ms>`（**诊断专用**：起播 2 秒后故意制造不同步，实测能造出
  ±450ms 上下的内容错位）。
- `native/av-heal-test.ps1`：5 条断言（正常播放不误报重锚 / 正常偏移本来就小 /
  真错位被发现并重锚 / 重锚后偏移回到 ≤150ms / 默认路线**没有**去 seek 声卡）。
- `native/pause-resume-probe.ps1`：暂停 →（可指定时长）→ 恢复的**内容级**偏移探针。
  ★ 判定"暂停后有没有错开"**不能用"画面 vs 音频时钟"**：画面就是被音频时钟调速的，
  那个差值恒等于 0，永远看不出错位（老探针就是这么被骗过去的）。必须用
  `AV明细` 里的 `可听=`（写出内容 − 排队）去和画面比。

### 8.5.1 暂停/恢复为什么还会错开，以及"无痕纠正"（2026-09-28 第二轮）

用户复述的症状把范围缩小到了一处：**不是暂停期间错开，而是暂停之后重新起播的那一刻**
错开，并且此后一直保持那个差值（不漂移）。不漂移 = 一次性错位，也就是"某一步把位置算错了一次"。
按这个方向找到两个入口，都修了，并且加了一层兜底。

#### 入口 1：恢复时 `Start()` 之后读到的"设备待播"不可信

`playedFrames = 写入 − 丢弃 − 待播`。暂停时设备停了、播放位置**必须保持不变**；
但 `Start()` 之后立刻读 `GetCurrentPadding()`，某些驱动会返回 0（缓冲区刚重建/还没被认领），
于是"已播帧数"凭空前跳整整一个设备缓冲（最多 200ms）→ 时钟前跳 → 画面丢帧追上 →
而缓冲里那段**没播**的音频恢复后照旧播出来 → **声音永久落在画面后面**。

老写法取 `max(暂停前, 恢复后)`，恰好把这个假读数**当真的保留下来**。现在固定用暂停前的读数，
`Start()` 之后的读数只当诊断打出来。日志里那行就是判据：

```
[host] 恢复：写入=235680 丢弃=9600 待播 9600→9120 帧，已播 216480→216960（跳变 10ms）
```

`跳变` 若是 200ms 左右，就是踩到了这个坑；修好后本机实测 0~10ms。

#### 入口 2：暂停超过 3 秒 → 恢复后第一次 tick 就误判"音频时钟停滞"

`MediaClock::tick()` 用"音频值多久没前进"来判定停滞（>3 秒 → 切挂钟）。
暂停期间 tick 直接返回（暂停不算停滞 ✓），但 `lastAdvance` 停在**暂停前那一刻**；
于是暂停一久，恢复后第一次 tick 立刻判定停滞并切到挂钟 —— 挂钟一旦接手，
画面按挂钟走、声音按自己的位置走，两边从那一刻起就靠不住地对齐了。

修法：`setPaused(false)` 里把 `lastAdvance` / `lastAudioValue` 重新计到当下。

#### 兜底：默认开启的"重锚时钟"纠正（不动声卡）

前两个入口是**具体原因**，但"错开了而且不纠正"这件事本身也说明系统缺一层兜底：
以前只有 `--av-correct`（把音频 seek 到画面），默认关闭 —— 用户报的正是"不能纠正"。

现在默认路线的动作是 **`MediaClock::anchor(可听内容位置)`**：

- 它**不动声卡一个字节**，所以没有跳音、不需要网络、不需要重新解码；
- 锚定之后 `clock.now() == 听到的内容位置`，呈现线程自然把画面拉回同一位置
  （落后就等，领先就把排队的帧丢掉追上来）；
- 它同时覆盖"时钟自己跳了"这一侧，因为锚定把时钟**拉回真实内容位置**。

保守判据（一条都不放宽）：可听内容估计可用 + 音频还是主时钟 + 不在定位中 +
偏移 ≥300ms + 连续 4 次采样（≈2 秒）+ 相邻采样差 ≤120ms + 离最近一次音频不连续 ≥4 秒
（seek/清缓冲/**暂停恢复**都算不连续点）+ 距上次重锚 ≥3 秒 + 整个播放最多 8 次。

日志与实测：

```
[host] ⚠ 音画偏移 -474ms（声音领先画面）→ 已把**时钟**重锚到音频内容 8314ms（声卡不动，画面自己追上去；第 1 次）
```

| 场景 | 重锚前最大偏移 | 重锚后最大偏移 |
| --- | --- | --- |
| 正常播放 8 秒（误报检查） | 29ms | 0 次重锚 ✓ |
| 人为注入错位（`--debug-audio-lag 700`） | 485ms | **29ms** |
| 暂停 5 秒后恢复 | 8ms | 19ms |
| 暂停 30 秒后恢复 | 28ms | 16ms（暂停记账 `跳变 0~10ms`） |

★ 注意"暂停 5/30 秒"那两行是**内容级**偏移（可听 vs 画面），不是"画面 vs 时钟"。
（上表是 2026-09-28 本机 bbb.mp4 + 真实声卡的实测值，`native/av-heal-test.ps1` 与
`native/pause-resume-probe.ps1` 会重跑这些数字。）


### 8.6 与 Java 侧的契约（**不能动**）

- 命令行参数（`HostSession` 传的那些）、控制管道动词与回执格式
  （`hello / status / pause / seek / volume / loop / av-offset / quit`）；
- 共享状态块 `spike/shared/cineduct_spike_status.h`：**原有字段的偏移一个都没动**。
  v4 只在**末尾追加**了 4 个诊断字段（`decodeMode@372` / `buffering@376` / `seekHealCount@380` /
  `droppedLate@384`，`kVersion` → 4）。追加是安全的：老 jar 读老偏移依然正确，
  所以 Java 侧**不做版本号强校验**（只校验 `magic`）。**规矩：以后要加字段也只许追加，不许插入/改序。**
- 行为约定：片尾不退出进程而是"保持最后一帧待命"、`loop 1` 回卷、暂停冻结画面与位置、
  暂停中 seek 立刻回执、音频坏了不牵连画面、非零 PTS 原点归一。

### 8.7 v4/v5 状态字段给上层带来了什么

| 字段 | 值 | 上层拿它做什么 |
| --- | --- | --- |
| `decodeMode` | 1 硬解 / 2 软解 / 3 硬解+CPU回拷 | 硬解不可用时子进程会**自动**回退软解、设备没有 VideoProcessor 时会回拷 CPU —— 以前完全看不见，玩家只感觉"风扇狂转/掉帧"。现在 `MediaSession.reportHostDiagnostics()` 会在变化时打一条日志，`/cineduct status` 也会显示 |
| `buffering` | 1 = 呈现侧没有新帧可出 | UI/诊断可以显示"缓冲中"，也能区分"卡住"与"没人看" |
| `droppedLate` | 累计迟到丢帧 | 正常追赶 vs 解码跟不上（数量速率） |
| `seekHealCount` | 累计定位自愈次数 | 这个流不能精确跳转时，上层能给个提示而不是"莫名奇妙的落点" |
| `videoPtsMs`（v5） | 最近发布帧的媒体时间 | 与 `mediaPositionMs` 一减就是**时钟级**音画偏移（★ 内容级偏移只有 host 日志里有，见 8.5.1） |
| `clockHealCount`（v6） | 累计**音画偏移自愈**次数（重锚时钟） | 正常播放恒为 0；>0 = "这次播放真的错开过"，`reportHostDiagnostics()` 会报一条明确事件，`/cineduct status` 显示「音画自愈」 |

> Java 侧读法见 `HostSession` 的 `decodeModeId()/decodeModeName()/buffering()/droppedLateFrames()/seekHealCount()/videoPtsMs()/clockHealCount()`；
> 日志提示在 `MediaSession.reportHostDiagnostics()`（渲染线程每帧看一眼，**值变了才打日志**，不刷屏）。

### 8.9 子进程 → 进程内引擎的**回退**：审计与修法（2026-09-28）

回退的触发点一共五处，全部都在 `MediaSession` 里：

| 触发点 | 触发条件 |
| --- | --- |
| 起播时 | 配置 `gpuHostEnabled=false` / 找不到 exe（`HostSession.start` 返回 null） |
| 推迟启动兜底 | `spawnHostNow` 起不来 |
| 就绪超时 | `awaitRing(12s)` 没过（环没建出来 = 首帧没解出来） |
| 互操作失败 | `GlInterop.probe` 返回 null（两块卡/驱动不支持） |
| 自愈阶梯用尽 | `checkHostHealth` 判崩溃/卡死（8 秒无新帧），60 秒窗口内重启满 3 次 → `failHost`（**不再回头**） |

审计发现它**缺一整套状态交接**，也就是说"回退"实际上退成了"重播"：

1. **位置没交接（最严重）** —— `ensureEngine()` 只认 `pendingSeekMs`（只有用户刚点过 seek 才有值），
   正常播放时是 -1，于是子进程放到 5 分钟崩掉，引擎从 **0** 开始放：进度条归零、玩家白看。
2. **暂停没交接** —— 只交接了音量/静音/循环。暂停中崩掉的话，回退后引擎会**自己出声放起来**，
   而 UI 还显示暂停（玩家下一步只会觉得"见鬼了"）。
3. **暂停中回退会黑屏** —— `acquireVideoFrame()` 在暂停时恒返回 null，而"补一帧"只在
   `forceAllocate` 时调用；回退时纹理是旧的、`textureAllocated` 已经是 true → 永远不去要那一帧。
4. **重启与回退的竞态** —— `doRecover()` 关掉旧进程后没再确认 `mode`：这几秒里若已回退，
   它会照样起一条新子进程并挂上来 → **引擎在放 + 子进程也在放**（0.3 秒两条音频的翻版）。
5. **GL 互操作对象在错误的线程关闭** —— `GlInterop` 明确约定"所有方法必须在渲染线程"，
   而 `failHost()` 有三个调用点在**后台重启线程**里，却直接 `interop.close()`
   （里面是真 `glDeleteTextures` + `wglDXCloseDeviceNV`）。对照：`rebuild()`/`doRecover()`/`close()`
   都是打 `needsGlReset` 标记、交给渲染线程 —— 只有 failHost 是个例外。
6. **渲染线程可能被堵 4 秒** —— `HostSession.close()` 是"等 2 秒优雅退出 + 等 2 秒 destroy"，
   而 failHost 可能就在渲染线程上被调用。
7. **回退后可能永久没声音** —— `openAudio` 打开失败的降级序列走完就放弃（纯视频），
   而回退场景里我们**刚刚强杀掉**一个可能占着独占端点的子进程，端点释放不是瞬时的。

修法（全部落在 `MediaSession` / `HostSession` / `MediaEngine`）：

- `failHost()` 里先在锁内**把 mode 切成 JAVA**（这样 doRecover 再想挂新进程也挂不上），
  再读 `h.mediaPositionMs()` 存进 `resumeSeekMs`（**必须在关闭之前读**：close 会释放状态环），
  然后 `abandon()` 强杀，最后 `ensureEngine()`。
- `ensureEngine()` 补齐交接：`resumeSeekMs`（其次 `pendingSeekMs`）→ `created.seek(pos)`，
  并把它同时记成 pending（`timeMs()` 的乐观窗口 8 秒，避免进度条先归零再跳回来）；
  `pauseWanted` → `created.pause(true)`。
- `uploadJavaFrame()`：只要 `!javaFrameUploaded` 就去要"暂停位置那一帧"（暂停中回退不再黑屏）。
- `doRecover()`：关掉旧进程后、以及 `awaitRing` 之后挂新进程前，都在同一把锁里复查
  `closed || mode != Mode.HOST`，命中就 `abandon()` 刚起好的进程并作废这次重启。
- `failHost()` 不再直接 `interop.close()`，改为 `needsGlReset = true`（渲染线程下一帧释放）。
- 新增 `HostSession.abandon()`（`close()` 重构为 `shutdown(graceful)`）：放弃进程时直接强杀，
  最多等 800ms，不再让渲染线程等 4 秒。
- `MediaEngine.openAudio()`：设备打开失败时**等 400ms 再试一轮**（同一套降级序列）。

**怎么现场验证**（这是"能不能正常回退"唯一真正的答案）：

```powershell

```

期望看到：位置**不回到开头**、暂停中不会突然出声、无黑屏、没有两条声音。
