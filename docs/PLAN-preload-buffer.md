# 计划：预测式提前缓存 + 卡顿闸门（C++ 宿主侧）

> 状态：**P1（L0 观测 + L1 水位）与 P2（L3 闸门）已在 C++ 侧实现并构建部署**；
> L2 预读线程、Java 侧读数/豁免、L4 自适应、L5 服务端延迟仍未做。
> 适用：`cineduct-host.exe`（native/host）+ Java 侧 `MediaSession` / `ScreenClientState`
> 目标：客户端卡顿时，视频"等缓存"而不是"丢帧追服务端进度"。

## 落地情况（2026-10-25）

| 层 | 状态 | 落点 |
| --- | --- | --- |
| L0 观测 | ✅ | 状态块 v11 追加 9 字段（`cineduct_spike_status.h`），由 `video_pipeline.cpp` 的 `updateStatus()` 写 |
| L1 水位时间化 | ✅ | `packet_queue.*` 改为 PTS 跨度限深（默认 4000ms / 128MB / 2000 包） |
| L1.5 起播预缓冲 | ✅ | `evaluateBufferGate()` 的 ① 段（默认 1500ms，按跨度上限钳住） |
| L3 卡顿闸门 | ✅ | `enterGate()` / `leaveGate()`：供给见底 + 消费者停取帧两条判据，6 秒硬上限 |
| L2 预读线程 | ⬜ | 需要自定义 AVIO；分片流有 seek 语义风险 |
| Java 侧读数 | ✅ | `HostSession` 读 v11（`bufferSummary()` 等）、`MediaSession.hostWaitingForBuffer()`、`checkHostHealth` 闸门豁免、`ScreenClientState` 闸门期间跳过 5 秒安全网、参数经 `FfmpegConfig` 透传 |
| L4 自适应 / L5 服务端延迟 | ⬜ | — |

已验证：本地 1080p30 文件正常播放（30.0~30.5fps、零丢帧）、片尾、预缓冲门限钳制；
**未验证**：闸门在真机上被消费者停顿触发（需要游戏进程取帧，只能进游戏测）。

## 0. 一句话结论

**只加深缓存解决不了这个问题。** 现在本地播放位置是"音频已播 + 挂钟"算出来的
（`native/host/src/video_pipeline.cpp:1241-1245`），它**不知道渲染侧有没有卡**：
卡 1 秒，时钟就走 1 秒，恢复后按 `kLateDropMs = 100ms` 的判据把积压的帧全丢掉追赶
（`video_pipeline.cpp:36`、`2011-2016`）。所以必须两条腿一起走：

1. **把缓冲做成按时间计的水位并加深**（现在约 0.1~1 秒，目标 3~6 秒）；
2. **加卡顿闸门**：检测到本地停顿就冻住时钟 + 声卡，把这段记成"本地滞后"，之后有限速追回，
   而不是丢帧。

再往上才是"预测"：用实测的卡顿时长分位数和下载速率，自动决定水位要多深、预取要提前多少。

## 1. 现状（证据）

| 事实 | 位置 |
| --- | --- |
| 包队列有界 60 包 / 8MB，满了 demux 就睡 | `native/host/src/packet_queue.h:53-57`、`:8` |
| 帧队列刻意只有 3 帧（延迟换手感） | `native/host/src/frame_queue.h:4-8`、`:46` |
| 进状态块的位置 = 主时钟，不是"已呈现帧的 PTS" | `native/host/src/video_pipeline.cpp:1241-1247` |
| 迟到 > 100ms 且队列里还有新帧就丢 | `video_pipeline.cpp:36`、`2011-2016` |
| `buffering` 位只写状态块做诊断，不反作用于时钟 | `video_pipeline.cpp:1294` |
| Java 侧 400ms 迟滞把它翻成 BUFFERING，仅状态可见性 | `src/main/java/dev/mediafix/player/MediaSession.java:106`、`:1420-1433` |
| 服务端权威位置按**真实时间**推进 | `src/main/java/dev/mediafix/screen/ScreenEntity.java:486-496` |
| 客户端只在锚点代次变化时对齐；另有 5 秒安全网 | `src/main/java/dev/mediafix/client/ScreenClientState.java:284-310` |
| 落盘下载缓存曾存在，因合规**整条移除** | `src/main/java/dev/mediafix/config/StreamConfig.java:19-20`、`src/main/java/dev/mediafix/ui/Notice.java:16-17` |

三条推出结论：

- **预取深度被封顶**：队列一满 demux 就停读，所以"提前下载"最多只到队列满那一刻 ≈ 1 秒
  （1080p60 按 60 包算）。想真提前缓存，必须让读网络这件事不再受播放位置限流。
- **卡顿 = 规定好的丢帧**：时钟不冻结，恢复后积压帧全部"迟到"，只能丢。
- **缓存不能落盘**：合规原因只能放内存，且必须有上限，不能变相成为"下载"。

## 2. 为什么"只加缓存"不够（1 秒卡顿的时序）

```
卡顿开始  帧队列 3 帧（≈50ms） → 呈现线程不跑
+0~1000ms 解码线程填满 3 帧后阻塞 → demux 填满 60 包后阻塞（网络读停）
          音频线程照跑 → 时钟 +1000ms
+1000ms   渲染恢复：队列里那 3 帧全部迟到 >100ms → 连丢 3 帧
          丢完队列空 → 等解码 → 新帧还是迟到 → 继续丢，直到追上时钟
          画面表现：跳 1 秒 + 花屏/卡死若干帧；包队列被抽干 → 叠加网络等待
```

缓存加深只能让"抽干"晚一点发生，**丢掉的那 1 秒内容不会回来**。要拿回来，只能让时钟停下等。

## 3. 方案分层（每层可独立开关，按顺序上）

### L0 观测（先做，零风险）

新增状态块字段（**只许在末尾追加**，`kVersion` → 11，见 `native/spike/shared/cineduct_spike_status.h:11`）：

| 字段 | 含义 |
| --- | --- |
| `packetBufferMs` | 包队列里首尾 PTS 跨度（视频侧真实可用秒数） |
| `frameBufferMs` | 已解码未呈现帧对应时长 |
| `bufferLevelMs` | 上面两者之和（"水位"） |
| `prefetchAheadMs` | 预读头领先播放位置多少毫秒（L2 后才非 0） |
| `hitchCount` / `hitchTotalMs` | 本地呈现停顿次数与累计时长 |
| `localLagMs` | 本地位置相对服务端权威位置的滞后（Java 侧填） |

采集方式：`PacketQueue` 入队/出队时记录首包 PTS；呈现线程每帧算一次。写入点跟
`video_pipeline.cpp:1238` 的 `updateStatus()` 同一处。

验收：`pipeline-test.ps1` 跑通，日志里能看到 bufferLevelMs 随时间的变化曲线（手写解析即可）。

### L1 水位时间化 + 包队列加深

- `PacketQueue` 的限额从"60 包 / 8MB"改为"**PTS 跨度 ≤ targetMs** 且字节 ≤ 上限"，
  `targetMs` 默认 4000，配置可调；包数上限保留做兜底（防 PTS 缺失的流）。
- **帧队列不动**（仍 3 帧）：它直接决定暂停/seek 后的清队列代价和操控手感，
  加深只会让画面更迟。卡顿余量要靠 L2/L3，不是靠堆帧。
- 上限受内存钳制：4K 高码率 4 秒 ≈ 100MB 量级，需按"码率 × 秒数"封顶（默认 128MB）。

验收：`pipeline-test.ps1` 的出帧节奏与 seek 落点不变；长跑 10 分钟内存不涨。

### L2 预取与播放位置解耦（这才是"提前缓存"）

现状：`av_read_frame` 在 demux 线程里同步读网络，队列满就停。改法：

- 自定义 `AVIOContext`，把**读回调接到一条预读线程**上；预读线程把网络字节写进
  内存环形缓冲（默认 32~64MB），游标独立于播放位置推进。
- 预读窗口 = 播放位置 + `targetMs` + 卡顿余量；环形缓冲满才停。
- 收益：卡顿时数据继续进、seek 回退不重下、断流重连不丢已有数据。
- 必须保留：`interrupt_callback` 语义（`video_pipeline.cpp:243`、`:353-359`）、
  seek 三阶段握手、"坏定位"判定逻辑。
- 注意**两条链**：视频在宿主进程里，音频在 `audio_source.cpp` 自己的上下文里
  （`reconnect()` 在 `:177`）。音频侧已有 `audioQueuedMs` 水位（状态块 @628），
  预读层要么两边都做，要么先只做视频、音频靠现有环形缓冲。

风险点：HLS/DASH 分片 + 自定义 AVIO 的 seek 语义（分片内 seek 会失败）。
对策：分片流先只做"顺序读的预读"，不接管 seek；`--url` 里出现 `.m3u8` 就走降级路径。

### L3 卡顿闸门 + 有限速追赶

- **卡顿检测**：呈现线程每帧记录 `steady_clock` 间隔；间隔 > 200ms 记一次 hitch
  （GC/区块加载/着色器编译/显卡驱动停顿都会体现成这个）。
- **闸门动作**：`clock.invalidate()` + `audioSink.setPaused(true)` + 保持最后一帧。
  此时 `mediaPositionMs` 停住 —— 进度条不再"按服务端/时钟自己往前走"。
- **恢复**：水位回到高水位线（`targetMs × 0.75`）后解冻。滞后量记为 `localLagMs`，
  用两种方式消费：
  - **慢追**：按 `1 + min(0.1, lag / 20000)` 的速率消化（每 N 帧丢 1 帧，或就地快进
    已预读的包），10~20 秒内追平；
  - **不追**：滞后 < 阈值就留着不管（多人影院更好看：宁可各自差 300ms，也不要跳画面）。
- **与 Java 侧联动**（关键）：`ScreenClientState` 的 5 秒安全网
  （`DRIFT_NET_MS`，`ScreenClientState.java:45`、`:300-309`）现在会把这种滞后判成"偏离权威位置"
  并 seek —— 闸门开启期间必须跳过这条判定，否则一次卡顿换来一次真 seek（重开两条 CDN 连接）。

验收（新增 `native/stall-test.ps1`）：
1. 测试模式注入一次 800ms 渲染停顿；
2. 断言：`droppedLate` 不增加、`mediaPositionMs` 在该段**不前进**、恢复后 3 秒内 `localLagMs` < 300；
3. 无卡顿时：正常播放 `localLagMs` 恒 ≈ 0，`droppedLate` 与改造前一致。

### L4 预测（自适应水位）

用 L0 的观测量做估计，都是现成的滑动窗口就能算：

| 输入 | 用途 |
| --- | --- |
| hitch 时长 p95（近 10 分钟） | `targetMs ≥ p95 × 1.5 + 500` |
| 下载速率 EWMA / 当前码率 | 预取能不能撑住水位；撑不住就先降码率（`AbrController` 已有） |
| 解码耗时 p95 | 决定帧队列是否要临时 +1 |

输出：`targetMs ∈ [1500, 8000]`、`prefetchAheadMs`、闸门门限。
约束：**不要**为了抗卡顿无限加深 —— 内存有上限，且延迟越大 seek/暂停越迟钝。

### L5 多人影院：服务端统一延迟（可选，但推荐）

客户端各自加本地延迟会互相不同步（同屏几个玩家看到的画面差几百毫秒）。
干净的做法是**服务端也承认这个延迟**：`ScreenEntity` 增加 `playbackDelayMs`（默认 = 水位），
`projectedPositionMs()` 统一减掉它（`ScreenEntity.java:486`）。
于是所有人都在权威位置后 D 毫秒、彼此仍同步，且每个人都天然有 D 的余量。

## 4. 明确不做

- **不落盘**：合规红线（`StreamConfig.java:19-20`）。缓存只在内存，进程退出即消失。
- **不加深帧队列**：延迟代价大于收益，卡顿余量靠 L2/L3。
- **不改已有字段偏移/语义**、不改 `hello/status/pause/seek/volume/loop/av-offset/quit`
  这些动词（`native/README.md:206-215` 的契约）。新能力要么追加字段，要么加新动词。
- **不让"缓冲"变成无限挂起**：必须有一条兜底（水位够 / 超时 4 秒 / 片尾），
  否则直播或坏源会永久停在缓冲 —— 进程内引擎踩过这个坑（`MediaEngine.java:1182-1189`）。

## 5. 分期与工作量

| 期 | 内容 | 风险 | 估算 |
| --- | --- | --- | --- |
| P1 | L0 观测 + L1 水位时间化 | 低（纯加字段/改限额） | 半天 |
| P2 | L3 卡顿闸门 + Java 侧安全网联动 | 中（会听见"停一下"） | 1~2 天 |
| P3 | L2 预读线程（先只做顺序读，m3u8 走旧路） | 中高（AVIO/seek 语义） | 2~3 天 |
| P4 | L4 自适应 + L5 服务端延迟 | 低 | 1 天 |

P1+P2 就能消掉"卡顿 → 丢帧 → 看着像加载不出来"这个主症状；P3 才真正把"提前缓存"
从 1 秒推到 4~6 秒。

## 6. 待你确认的三个决策点

1. **多人影院要不要统一延迟 D**（L5）？要，就得动服务端同步包；不要，就只做本地，几个人会各自差一点。
2. **卡顿时允许"声音也停一下"吗**？闸门 = 声卡暂停，听起来是"卡一下再继续"；不允许就只能丢帧。
3. **优先解决哪个**：① 网络/解码供不上（无网速抖动时也卡）→ 先做 L2；
   ② 游戏自身掉帧/加载区块时卡（网络没问题）→ 先做 L3。两个都做则按上面分期。
